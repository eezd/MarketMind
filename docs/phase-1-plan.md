## 1. 目标、阶段与边界

### 1.1 项目总体阶段

1. **数据获取**：采集三个来源、六个指定入口的新闻与快讯，可靠写入 PostgreSQL，并提供采集管理接口。
2. **数据筛选及优化**：分类、跨来源归并、汇总，交由 AI 生成可追溯的总结。实现对应处理与管理接口。
3. **页面呈现**：展示总结文章、行情趋势和预测，完善管理后台，复用前两阶段接口。

第一阶段交付的是“可采集、可追溯、可恢复、可人工干预”的系统，不只是六个能运行一次的 Spider。

**个人自用原则**：系统仅供用户本人使用，优先实现稳定采集和便捷操作，不按企业平台建设。复用现成库和框架默认能力，不为规范而增加抽象、重复文档、审批流、合规报表或独立监控平台；不提前实现尚未需要的分布式设施。普通实现细节由开发时按现有模式决定，不逐项要求用户确认。保留已明确的 `@antfu/eslint-config`、单管理员基本鉴权、凭证保护、生产数据保护、幂等落库和来源故障隔离；个人自用不改变既定内容访问边界。接口说明优先使用 FastAPI 自动生成的 OpenAPI，部署与恢复说明以可操作为准。

### 1.2 第一阶段范围

- 六个入口的列表发现、快讯文本及关联文章正文采集。
- 原始内容存档、最小格式规范化、来源内去重、内容修订留存。
- 定时采集、优先回补最近 48 小时、网页端自定义时间范围补抓、请求失败重试、异常隔离与任务恢复。
- IP 代理池管理、健康状态、站点级限速与熔断。
- 金十登录状态检测、官方登录二维码展示、扫码验证和会话复用。
- 单管理员认证、任务/代理/登录/日志/数据查询接口。
- 第一阶段提供最小运维后台：管理员登录、扫码、代理管理、任务监控与干预、自定义回补、只读采集数据页；第三阶段再完善总结文章与内容呈现。
- 部署配置、数据库迁移、任务运行恢复说明及验收记录；不包含备份策略与备份还原验收。
- GitHub Actions 自动检查并创建日期版本的源码 Release；不发布 Docker 镜像。
- 三个来源独立获取，单来源异常不阻塞其余来源；后台提示与 Telegram Bot 告警。

### 1.3 不在第一阶段实现

- AI 总结、语义分类、跨来源相似新闻合并、文章生成。
- 实时行情数据接入、趋势算法、预测模型、交易执行。
- 多用户、多租户、复杂角色权限、代理供应商自动购买：按用户要求明确不需要实现，后续阶段也不作为默认建设范围。
- 全站递归爬取、无限历史回补、图片/视频文件下载、OCR。
- 绕过付费墙、验证码或访问控制；破解私有签名及风控机制。

**后续依赖提醒**：新闻不是行情报价。第三阶段若要展示“当前行情”和验证预测效果，第二阶段设计时还需单独确认授权行情源、市场范围、预测周期和评估指标，不能把新闻摘要当作实时行情。

## 3. 采集内容与运行参数

普通正文、快讯全文、媒体仅链接、付费仅元信息、外站仅列表信息的五项边界已确认；分钟级时效和最近 48 小时回补已确认。其余限速、重试等为建议初值，不是网站承诺或已经达成的指标。

### 3.1 内容范围

- 快讯：完整可访问文本、源 ID、原链接、发布时间、重要性标记和来源标签。
- 文章：标题、摘要、完整可访问正文、作者、发布时间、修改时间、图片链接。
- 原始 HTML/JSON 与清洗文本分开保存；清洗只去除无关标记，不做 AI 改写。
- 图片、音视频仅保留元信息或链接，不下载媒体文件。
- 发现入口限定为六个页面；仅沿其新闻详情和分页链接采集，不扩展到热门推荐、专题、行情等其他栏目。
- 站点必需的 API/CDN 域名在验证后显式加入白名单；每次重定向也验证目标。
- 外站转载链接默认保留标题、摘要、原链接，标记 `external_link`，不自动扩大到微信公众号等外站全文采集。
- 付费正文默认不采集；保留合法可见元信息，标记 `paywalled`。用户另行确认订阅权限和内容使用权后才能调整。
- 正文不可得时明确标记 `pending / complete / summary_only / paywalled / external_link / unavailable`，不把摘要冒充完整正文；解析失败另有错误码，不伪装成无新闻。

### 3.2 调度与时效

| 参数 | 建议初值 | 边界 |
| --- | --- | --- |
| 快讯入口轮询 | 60 秒，约 ±20% 抖动 | 受站点许可和全局限速约束 |
| 文章入口轮询 | 5 分钟，约 ±20% 抖动 | 详情请求同样计入预算 |
| 默认历史回补 | 优先最近 48 小时，每执行批次最多 100 页 | 用户确认：初始启动及停机恢复仅自动补最近 48 小时，更早缺口只提示，由管理员在网页指定范围补抓 |
| 实时重叠窗口 | 最近 30 分钟 | 加上最近 24 小时定期复查，捕获迟到和修改 |
| 自定义历史回补 | 网页选择来源/入口和起止时间 | 无固定 48 小时范围限制；分批执行、保存进度，受来源历史可访问范围限制 |
| 单来源并发 | 1 | 同来源不同 Spider 共享预算，不能各算一份 |
| 单来源请求间隔 | 最低 3 秒，开启 AutoThrottle | 详情、重试、浏览器数据请求都计入来源预算 |
| 网络请求超时 | 30 秒 | 登录交互另有会话超时 |
| 瞬时故障重试 | 最多 3 次重试 | 统一尝试计数，避免多层重试相乘 |
| run 运行上限 | 实时 10 分钟，回补 60 分钟 | 超限记录中断点，不永久占用执行槽 |

站点要求更严格时采用更严格配置。回补按“最近 48 小时优先、更早范围手动指定”安排历史任务，不阻塞实时采集。实时与回补分别保存任务、检查点和执行配额，共享来源限速；回补到达单批页数/运行时间上限后分批续作。每次领取请求前检查到期实时任务，优先让行，不能等待整个百页批次或长回补 run 完成才执行实时采集。未覆盖窗口记录 `coverage_gap`；历史不再可访问时报告实际缺口，不标记全量成功。

用户接受分钟级目标：快讯轮询 60 秒、文章 5 分钟；健康且允许采集时，快讯首次可发现至入库 P95 不超过 120 秒，文章不超过 10 分钟。首次可发现时间需通过受控观察取得；同时报告发布时间至入库延迟，不能把网站延迟发布算作本系统的采集耗时。

## 4. 架构与职责

```text
最小运维后台 -> FastAPI -> PostgreSQL（指定生产实例）
                            ^
单实例调度器 -- 持久化任务/控制指令
    |                       |
    +-> 见闻执行器 -> 独立 Spider / 队列 -> Pipeline
    +-> 财联社执行器 -> 独立 Spider / 队列 -> Pipeline
    +-> 金十执行器 -> 独立 Spider / 队列 -> Pipeline
                         |
                    金十浏览器会话

Redis：按来源隔离队列、限速与协调键
告警记录 -> 独立通知发送器 -> Telegram Bot
```

### 4.1 职责划分

- **FastAPI**：鉴权、配置校验、创建控制指令、查询状态；不在请求进程内运行 Scrapy reactor，也不靠 BackgroundTasks 执行长期采集。
- **调度器与来源执行器**：调度器只扫描到期计划、创建 run 和持久化指令；三个独立来源执行器分别拉起本来源固定 Spider 子进程，收集退出码、心跳和统计。调度器不等待某一来源采集或重试完成再调度其他来源。
- **Scrapy worker**：六个 Spider 按来源隔离，执行有限批次任务；不承载定时调度职责。来源级重启仅作用于本来源执行器，入口级操作只作用于指定 Spider。
- **Scrapy-Redis**：按 `source_id / collector_id / run_id` 隔离待抓请求及去重集合，异常来源积压不阻挡其他来源出队。
- **Pipeline**：通过 SQLAlchemy 事务直接写 PostgreSQL。Scrapy 异步链路不得执行阻塞数据库 I/O；使用兼容 asyncio reactor 的异步驱动和有界连接池，启动阶段验证兼容性。
- **Playwright 服务**：持有隔离浏览器上下文，完成登录和必要动态请求；不向前端泄露 Cookie/Token。

初始只部署一个调度实例，仍使用数据库唯一约束与行锁防重复创建 run。未来扩容执行器之前，先验证共享限速、租约和命令隔离，不承诺第一阶段就具备多机高可用。

### 4.2 来源故障隔离与后续节点扩展

- 华尔街见闻、财联社、金十分别拥有执行器进程/容器、任务队列、浏览器进程（需要时）、会话、熔断状态和重试预算；同一来源两个入口共享本来源访问预算，不共享失败开关。
- 单来源登录失效、HTTP 错误、解析异常、卡死、内存超限或人工重启，只暂停/重启受影响来源或入口；其他两路继续获取、入库和调度。不可等待三路全部成功才提交新闻。
- 为每个来源设置有界 CPU/内存、数据库连接池、事务/锁等待超时和队列领取配额，避免一个来源耗尽共享资源。代理连通性故障可影响使用同一代理的来源，但目标站点封禁只更新对应来源的代理健康状态。
- 来源事务不共享跨来源业务锁；第 9.3 节变更游标也按来源隔离，避免某一路异常事务锁住全部新闻提交。
- 独立运行不等于基础设施高可用：同一宿主机、生产 PostgreSQL、Redis 或共同网络整体故障仍可能影响多路。这些公共依赖故障需单独显示，不宣称第一阶段能自动跨机容灾。
- 第一阶段采用独立调度器和三个执行器边界；预留 `node_id`、允许执行的来源和会话所属节点，单机也使用明确节点身份。未来启用多机时增加节点注册、健康查询、后台来源到节点绑定与受控迁移能力，不在本阶段提前建设远程管理页面。
- 跨网络部署后，金十浏览器与其采集会话必须使用同一节点出口或同一粘性代理；切换节点先停止旧租约、重新验证会话再运行。全局来源限速不能因节点数量增加而放大。

### 4.3 Scrapy-Redis 的采用边界

采用 Scrapy-Redis，但不使用其 Item Redis Pipeline 替代 PostgreSQL 入库，也不把它当作完整的业务调度和管理平台。

本次读取的上游源码中，请求通过 pop 从队列移除，没有与“新闻成功入库”绑定的 ACK。因此：

1. Redis 队列持久化不等于在途请求不丢失。
2. 请求指纹去重不等于新闻业务去重。
3. 请求已出队后进程崩溃，需要依靠持久化任务记录恢复。

按下面的 PostgreSQL 任务账本方案实现至少一次执行、数据库幂等落库；不声称网络请求恰好一次。无需同时引入 Celery、Scrapyd 和另一套调度系统。

## 5. 任务可靠性与人工干预

### 5.1 三层对象

- `collector`：六个逻辑采集器，保存计划、开关、来源和最近成功时间。
- `crawl_run`：一次实时轮询/回补执行，保存配置快照、触发者、进度和统计。
- `crawl_task`：一次可恢复的列表或详情逻辑工作，包含 URL/分页参数、run、尝试次数、状态、租约和错误。

先把任务写入 PostgreSQL，再投递 Redis；未投递成功的任务由扫描器重新投递。任务创建具有唯一业务键；重复投递只允许持有效租约的 worker 执行一次当前尝试。

- 任务租约建议 90 秒，每 15 秒续约；浏览器长请求按独立超时续约。
- 每次重新领取生成递增 attempt/generation；写入与完成更新必须检查 generation，拒绝过期 worker 提交。
- 响应解析后，在同一数据库事务内写新闻/修订、发现的后续任务和当前任务完成状态。
- 事务失败不确认成功；数据库不可用时停止领新任务，按有界策略等待，不能无限积压内存。
- worker 崩溃或租约过期，由恢复器将未完成任务恢复为可领取状态；实际领取与重启受第 5.3 节自动恢复预算及暂停状态约束，不能绕过人工接管门槛。检查点仅在对应批次已持久化后推进。
- Redis 丢失时从 PostgreSQL 未完成任务重建队列；Redis 启用持久化且与可淘汰缓存隔离，禁止因内存策略静默淘汰任务键。
- 请求去重键按 `source_id / collector_id / run_id` 隔离。恢复重投绕开旧尝试的请求指纹阻拦，由任务账本约束执行；否则“已见过 URL”会阻止重试。
- 不同轮次允许重新访问同一个列表 URL；同一轮过滤真正的重复链接和分页环。
- Redis 序列化采用受限 JSON 数据结构，Cookie/Token 不放入请求消息；避免接收不可信 pickle 数据。

### 5.2 状态与操作语义

采集器管理开关和运行健康状态分开：关闭调度不等于运行失败。运行状态至少区分 `queued / running / waiting_login / paused / succeeded / partial_failed / failed / cancelled / interrupted`。

| 操作 | 明确语义 |
| --- | --- |
| 禁用计划 | 不再创建新 run，现有 run 按原状态继续 |
| 立即运行 | 同一采集器、同一任务类型已有活动 run 时返回冲突及其 ID；实时与回补可分别持有活动 run，通过分批让行共享请求预算 |
| 暂停 | 停止领取新任务，允许在途事务完成，保留未完成任务和检查点 |
| 恢复 | 前置条件满足后继续同一个 run，不清空进度 |
| 取消 | 终止本次 run，撤销租约，保留已入库数据；不自动禁用未来计划 |
| 重试失败任务 | 只重投指定失败任务，保留尝试历史与原错误 |
| 重启采集器 | 停止受监督的旧执行实例，确认退出/租约失效，再恢复未完成任务；不是清库重爬 |
| 回补 | 网页选择来源/入口、起止时间，创建独立回补 run；按批次上限续作，显示覆盖范围、缺口、暂停/恢复/取消操作 |

“重启成功”必须依据新执行实例心跳和实际进度，不能仅依据发出启动命令。无法确认旧进程退出时，不并行拉起第二个写入者；数据库 generation 同时阻断旧尝试迟到写入。

操作先持久化为 `control_command`，执行器消费并回填结果；API 重启不会丢失已接受操作。管理端只能选择固定动作，不提供任意 shell、脚本上传或容器宿主机控制。

### 5.3 有限自动恢复与人工接管

- 用户选择有限自动恢复。初始策略为每来源滚动 30 分钟内最多自动重启 3 次；拉起即计一次，失败的启动也计入，预算持久化，不能因执行器重启归零。
- 适用于非预期进程退出，以及已确认旧进程停止的卡死恢复；有界退避后恢复未完成任务，不清空数据。HTTP 请求重试与进程重启分开计数，不把普通请求失败升级为重启。
- 预算耗尽后暂停受影响来源的自动执行，保留队列、检查点及故障原因，发送后台和 Telegram 告警；不能仅因时间窗口过去就自行解除暂停，也不能让下一轮定时任务绕过暂停。其他来源继续运行。
- 管理员检查后显式恢复或重启，解除暂停并开启新的恢复预算周期，记录操作。已知登录过期、验证码挑战和解析结构变化直接走对应等待/人工处理流程，不反复自动重启。
- 同一来源进程不能被应用恢复器和容器无限重启策略各自拉起；采集进程恢复统一由来源执行器管理，容器服务恢复后先读取持久化暂停状态及预算。

## 6. IP 代理池与限速

### 6.1 管理能力

- 用户已选择手工维护固定代理列表：支持单条/批量添加、修改、启用/禁用、健康检查及来源维度表现；不接供应商提取 API，不自动购买代理。
- 首期支持 HTTP 代理及 HTTPS 目标的 CONNECT；SOCKS 等协议需另行验证，不默认声明全支持。
- 保存代理协议、主机、端口、加密认证信息、来源适用范围、有效期、最近成功时间和连续失败数。
- 健康状态：`unknown / healthy / cooling_down / unavailable / disabled`；连通成功不等于目标站点可用。
- 健康检查访问受控目标，使用连接/读取超时；不把“代理可用”验证变成任意 URL 探测接口。
- 默认直连；添加代理到全局库存不自动改变出口，为某来源指定有序代理列表后，该来源优先使用指定代理。来源两个入口共享出口配置，避免登录会话和请求出口不一致。
- 来源出口配置使用 `proxy_ids`（有序、不重复）、`failover_enabled`（故障切换开关）和 `on_proxy_exhausted`（`direct` 或 `pause`）。不再使用旧 `required/direct` 模式；不允许自动选用未指定代理。
- 开启故障切换后，当前代理连接失败则依序尝试下一个指定且可用的代理；禁用、过期和冷却中的代理不参与。本轮不反复遍历同一代理，切换也受请求总尝试上限约束；若本轮预算耗尽仍有候选，延迟继续，不能误判为全部代理耗尽。
- 关闭故障切换时，只使用当前选定代理（初次为列表首项），不尝试其他代理。当前代理不可用时直接执行用户选择的耗尽策略。
- 所有允许尝试的代理均不可用时：`direct` 表示显式回退服务器直连并告警，`pause` 表示仅暂停对应来源并告警。指定代理时由用户明确选择策略；表单可预选 `pause`，保存后生效，不隐式授权直连。未指定代理的初始状态直接使用直连，不算故障回退。
- 记录并展示当前出口、代理顺序、切换原因、是否已回退直连和配置版本；配置变更在下次安全请求边界生效。在途请求不强行切换；暂停后不因健康探测成功自动恢复，需管理员显式恢复。
- 已回退直连或备用代理时保持稳定出口；优先代理恢复仅提示，不自动来回切换。下一次管理员应用出口配置或显式恢复时重新按顺序选择，金十按第 6.2 节重新验证会话。

### 6.2 故障分类

- 连接超时、代理握手失败：降低代理健康度，按已配置顺序及故障切换开关处理，不随机选择库存中的其他代理。
- HTTP 429：遵守 `Retry-After`；缺失时指数退避并加入抖动，降低整个来源的请求预算，不能立刻换 IP 继续原速率。
- HTTP 403/验证码挑战：暂停对应路径并告警，区分权限、登录、风控，不能统一判定为代理故障。
- 登录过期：进入 `waiting_login`，不惩罚代理，也不自动无限生成二维码。
- 站点 5xx：来源级退避；连续异常建议 5 次后熔断 10 分钟，仅低频探测恢复。
- 解析异常：保留脱敏响应样本、解析器版本和错误位置，暂停受影响采集器；不靠换代理掩盖页面改版。

限速采用共享 Redis 原子预算，维度至少包含来源和必要的账号；Scrapy AutoThrottle 只提供 worker 内部调节，不能代替跨 Spider/浏览器的共享预算。代理切换不增加来源总请求额度。

登录会话采用粘性出口：浏览器登录与后续采集保持一致的直连或代理出口。切换到备用代理或按用户策略回退直连时，先停止受影响的受保护请求，再验证新出口下会话是否可用；失效则等待扫码，不妨碍其他来源继续运行。不得每请求随机换 IP；代理必须来自可信渠道，始终校验证书，不为适配代理关闭 TLS 校验。429、403、登录失效和解析错误不能触发代理轮换或直连来绕过来源级退避/权限处理。

## 7. 金十扫码登录与第一阶段操作页

### 7.1 真实流程验证门槛

金十登录需求已明确，但当前未证实具体二维码登录协议。实现前需由真实浏览器验证：

- 登录入口是否支持用户期望的手机扫码，使用哪种 App，以及是否需要手机二次确认。
- 二维码是否随浏览器会话绑定、是否有明确过期时间、是否需验证码等额外操作。
- 登录后两个金十域名是否共享会话；必须分别验证，不能假定 Cookie 跨域有效。
- 采集所需会话仅为 Cookie，还是包含 localStorage、CSRF Token、浏览器绑定状态。

若官方流程不能提供可复用二维码或必须额外交互，记录具体阻塞并请用户确认官方支持的替代登录方式；不能伪造二维码、绕过挑战或宣称已完成扫码登录要求。

### 7.2 目标交互

1. 采集器识别明确的未登录响应，保存待处理任务并进入 `waiting_login`；公开路径可独立继续。
2. 最小操作页显示“需要登录”，管理员点击开始登录，后台创建一次 `login_attempt`。
3. Playwright 在隔离上下文打开官方登录页，取得官方二维码图像或实际二维码区域截图，返回受鉴权保护的图像接口。
4. 页面直接显示二维码、官方说明、过期信息和当前状态，用户手机扫码并确认；不要求用户手工复制 Cookie。
5. 后台以官方允许的间隔检查登录结果；只有受保护页面/数据请求验证通过才标记 `authenticated`。
6. 分域保存验证结果和会话版本，恢复授权范围内受阻任务。
7. 二维码过期后由管理员刷新，旧 attempt 作废；多个管理员页面不得生成互相覆盖的有效会话。

状态：`unauthenticated → qr_pending → authenticated`，并支持 `expired / failed / cancelled / action_required`；只有网站能可靠区分“已扫码”时才额外显示该中间态。

第一阶段最小运维后台范围已确认：管理员登录、六个采集器概览、运行详情与固定控制动作、代理管理、金十扫码、会话状态、自定义时间范围回补、只读采集数据页、后台告警及 Telegram 配置。回补表单显示时区，提交 ISO 8601 起止时间（含时区），使用 `[start_at, end_at)` 区间并校验起止顺序；可按来源/入口选择，显示各自进度和缺口。后台不提前开发公开新闻站、AI 总结或内容发布页面；第三阶段沿用其接口及前端基础，不另建一套鉴权。

只读采集数据页使用现有新闻查询 API，支持按来源、发布时间和正文状态筛选，分页查看列表，打开正文、原链接及修订记录。页面用于本人检查采集结果，不提供编辑、删除或发布功能；正文按不可信内容处理，优先纯文本呈现，不直接执行原始 HTML。

### 7.3 会话安全

- 仅管理员可读取二维码，响应 `Cache-Control: no-store`，不公开静态文件地址。
- Cookie、Token、storage state 加密存储，密钥由部署环境的秘密配置提供，不进入仓库或普通配置表。
- 会话资料不进入日志、队列消息、API 新闻响应和 AI 输入；浏览器数据目录限制访问权限。
- 二维码和未完成登录上下文过期即清理；保留脱敏状态审计，不长期保存二维码图像。
- 会话失效或撤销时停止使用旧版本；服务重启后重新验证会话，不直接相信上次状态。

## 8. 数据模型与入库契约

### 8.1 新闻相关表

| 表 | 核心字段 / 用途 |
| --- | --- |
| `sources` | 三个来源及许可/启用配置 |
| `collectors` | 六个入口、Spider 名称、计划、版本化配置 |
| `news_items` | 新闻稳定身份、规范 URL、当前 revision、首次/最近发现时间、撤回状态 |
| `news_occurrences` | 新闻出现在哪些入口、对应 run 和发现时间；同站同文跨入口不重复建正文 |
| `news_revisions` | 不可变版本：标题、摘要、正文、源标签、重要性、作者、发布时间、源修改时间、正文状态、内容 hash、观测时间 |
| `raw_documents` | 关联 revision/task 的原始 HTML/JSON、响应状态、抓取时间、解析器版本；不存认证头 |
| `news_changes` | 每次新增/修订/明确撤回的 change_id、revision_id、change_type，用于第二阶段增量读取 |

`news_items` 使用内部稳定 ID；业务身份优先使用 `(source_id, source_item_id)` 唯一约束。没有稳定源 ID 时使用来源内规范 URL；保留原 URL，不能去掉有业务含义的查询参数。两种身份后续对齐必须事务化处理，不能因首次缺 ID、随后有 ID 而新增重复新闻。

### 8.2 运行与管理表

- `crawl_runs`：来源/入口、触发类型、配置快照、时间范围、执行节点、状态、统计、心跳、覆盖缺口、实时/回补独立检查点。
- `crawl_tasks`：任务幂等键、请求参数、attempt/generation、租约、重试时间、错误与完成状态。
- `control_commands`：固定操作类型、目标、请求幂等键、执行状态和结果。
- `proxy_endpoints` / `proxy_source_health`：代理配置与来源维度健康度；`sources` 保存有序 `proxy_ids`、`failover_enabled`、`on_proxy_exhausted` 及配置版本，执行器记录实际出口和切换原因。
- `source_sessions` / `login_attempts`：加密会话、分域状态、版本、登录尝试和过期信息。
- `admin_users` / `admin_sessions`：单管理员和可撤销登录会话。
- `audit_events`：操作人、目标、动作、时间、脱敏变更及结果。
- `alert_events` / `notification_deliveries`：来源级告警、去重状态、Telegram 发送尝试与结果；通知失败不回滚新闻事务。

运行日志采用结构化文件并轮转归档，归档不删除；PostgreSQL 保存运行摘要和关键事件，不把每条调试日志重复写入数据库。所有已记录日志纳入持久化归档，不能依赖容器默认轮转删除。

### 8.3 数据不变量

1. 同来源同新闻重复采集不新增 `news_items`；跨来源转载暂不合并。
2. 实质内容变化新增 revision，不覆盖旧正文；hash 排除抓取时间、阅读量等无关波动字段。
3. 已有完整正文不能被一次未登录摘要或空响应覆盖；权限变化记录为访问状态/事件。源站明确更正可以新增版本。
4. 新闻、revision、change 记录与任务完成在同一事务提交；并发写由唯一约束和行锁处理。
5. 统一 UTC `timestamptz`，API 输出 ISO 8601；源时间原文及源时区单独保留。无发布时间时允许空值并标记，不拿抓取时间伪装。
6. 分开记录 `published_at`、`source_updated_at`、`first_seen_at`、`fetched_at`，供后续 AI 防止使用当时尚未获取的信息。
7. 列表暂时消失不等于撤稿；仅在明确证据下标记撤回，保留原版本及原因。
8. 标题、URL 或正文结构异常不能静默丢弃，需进入可查询的失败任务或质量问题记录。

用户明确要求从正式采集开始直接接入生产数据库，数据全部保留：新闻、所有修订、原始响应、变更记录、运行/任务记录、审计、告警和已记录日志均不设置自动到期删除。移除原始响应 30 天、日志 14 天、运行记录 90 天、审计 180 天等旧期限。允许压缩及持久化归档，但不能以归档为名丢失查询或溯源能力；监控数据库和归档容量，容量不足时告警并扩容，不自动删旧数据。敏感临时资料不属于长期业务存档：二维码、失效凭证和临时浏览器上下文仍按第 7.3 节清理，保留脱敏审计。

## 9. API 契约与未来阶段衔接

统一前缀 `/api/v1`，OpenAPI 作为接口契约。第一阶段实现本节采集相关接口，不只列出路由名。

### 9.1 接口清单

| 方法 / 路径 | 责任 |
| --- | --- |
| `POST /auth/login`、`POST /auth/logout`、`GET /auth/me` | 单管理员认证、退出和身份查询 |

| `POST /collectors/{id}/runs` | 创建实时或回补 run；回补接受 `start_at / end_at`，返回独立进度和实际覆盖范围 |

| `GET /audit-events` | 管理操作审计查询 |
| `GET /health/live`、`GET /health/ready`、`GET /metrics` | 存活、依赖就绪、受限监控指标 |
| `GET /alerts` | 查询来源告警及 Telegram 发送状态 |
| `GET /notification-settings/telegram`、`PATCH /notification-settings/telegram` | 查询脱敏配置、设置目标 chat_id 和启用状态；Bot Token 只写入不回读 |
| `POST /notification-settings/telegram/test` | 管理员显式发送测试通知，返回 command_id |

`/news/changes` 等静态路径需避免被 `/{id}` 路由误匹配。原始 HTML 的读取只提供受限下载或纯文本展示，禁止直接作为可信 HTML 渲染。

### 9.2 通用行为

- 管理接口全部鉴权；公开存活探针不泄露内部连接信息，metrics 仅内网/授权访问。
- 错误结构：`code / message / request_id / details`，details 脱敏；400/422 参数问题、401 未登录、403 无权限、409 状态或版本冲突、429 管理端限流、503 依赖不可用。
- 异步控制返回 HTTP 202 和 `command_id` 或 `run_id`；这表示已持久化接受，不表示执行完成。
- 运行、重启、重试、登录尝试等创建操作支持 `Idempotency-Key`，按管理员、路由和请求体绑定；同键不同请求体返回 409。
- 列表采用稳定排序和不透明游标，默认 50 条、上限 200 条；明确过滤条件和时间范围。
- 代理密码、会话凭证只允许写入不允许明文回读；日志与审计使用相同脱敏规则。
- 最小页面先用轮询查询，运行页约 5 秒，二维码状态查询依官方规则；不为了六个采集器额外引入 WebSocket 体系。

### 9.3 第二阶段数据输入

`GET /news/changes?cursor=...&limit=...` 返回 `items` 和 `next_cursor`；每条包含 `source_id / change_id / news_id / revision_id / change_type / observed_at`。可获取对应不可变 revision，而不是永远读取最新正文。`change_id` 在来源内递增，身份为 `(source_id, change_id)`；不透明 cursor 保存各来源已消费位置，不承诺跨来源全局提交顺序。

- 第二阶段保存自己的消费游标，以 `(revision_id, processor_version)` 幂等处理；不把 AI 状态写进原始新闻正文。
- 消费语义为可重放、至少一次；消费游标与处理结果需可靠提交。
- 不直接用普通自增 ID 最大值作为已提交高水位：并发事务可能先取得小 ID 后提交，导致漏读。
- 各来源新闻变更事务分别锁定本来源的变更序号行，在短提交区间内分配 change_id 并提交，保证来源内序号与可见提交顺序一致；锁内不做网络 I/O，设置事务/锁等待超时。不能使用一行全局序号锁，使一个来源影响其他来源入库。
- 接口公平轮询各来源，游标只推进本次实际返回的连续来源内变更位置；一来源暂无数据或采集失败不阻止返回其他来源的数据。变更历史全部保留，支持第二阶段启动与重放，不实现自动清理。
- 第二阶段再定义总结任务、分类规则、模型配置、生成结果和人工发布接口；第三阶段直接使用这些接口，不从采集表推测总结状态。

## 10. 管理认证、观测与部署

### 10.1 单管理员

- 部署初始化时设置一个管理员账号，密码通过交互输入或部署秘密注入；不提供固定默认密码，不开放注册。
- 密码使用 Argon2id 哈希；同源管理页使用可撤销的服务端会话，Cookie 设置 HttpOnly、SameSite，并对写操作验证 CSRF/Origin。仅本地 HTTP 开发配置关闭 Secure，生产 HTTPS 必须启用 Secure，不根据不可信请求头自动降级。
- 登录限流；修改密码撤销旧会话。不为单管理员引入角色管理系统。
- 限制可采集 URL、重定向和代理检测目标，拦截回环、云元数据等非预期网络访问；管理员提供的内网代理仅通过显式部署白名单允许，不能自动放开任意内网探测。

### 10.2 观测内容

每个来源/采集器显示：当前 run、状态、最后心跳、最近成功时间、下次执行时间、排队数、在途数、最老待处理时长、请求成功/失败、429/403、重试数、新增/更新/重复数、正文完整率、入库延迟、代理状态和登录有效性。
额外显示每来源当前直连/代理出口、代理切换开关、耗尽策略及最近切换原因；后台显示应用日期版本和提交 SHA，便于核对部署镜像。

- 存活不代表健康：分别判断进程心跳、成功响应和数据质量。
- 新增为零不直接报警；结合历史流量、页面结构、HTTP 状态和最近有效数据判断。
- 建议 60 秒无心跳标记失联；任务恢复仍以租约到期和 generation 为准。
- 必须记录登录失效、所有代理不可用、连续解析失败、持续限速、数据库/Redis 故障、队列积压和覆盖缺口事件。
- 第一阶段同时提供后台告警和 Telegram Bot 通知。至少通知需重新扫码、对应来源全部可用代理耗尽、持续采集失败和恢复；普通瞬时重试只记录，不逐次推送。
- 告警先持久化，由独立通知发送器投递；按来源、告警类型和事件状态去重，失败使用有界重试与退避，记录发送失败。Telegram 不可达不阻塞任何来源采集，也不引发无限通知递归。
- Telegram 仅发送来源、状态、时间、脱敏错误摘要和管理页链接，不发送新闻全文、二维码、Cookie、代理密码或 Bot Token；不提供 Bot 远程控制命令。Bot Token 秘密存储，目标 chat_id 和启用状态由管理员配置。
- 数据库整体不可用时不能依靠数据库告警表保证通知送达；依赖健康探测进程可直接尝试脱敏 Telegram 通知并记录本地持久化日志，恢复后补记事件。宿主机或所有外网出口失效时不承诺本机 Bot 能告警。

### 10.3 部署与恢复

服务：`api`、`scheduler`、`worker-wscn`、`worker-cls`、`worker-jin10`、按需来源独立 `browser-session`、`notification-worker`、`redis`、管理前端/反向代理；连接用户指定的生产 PostgreSQL。开发与验收另用隔离 PostgreSQL/Redis，不能把生产实例当作可重建的 Compose 测试容器。Spider 在各来源执行器中以受监督子进程隔离，FastAPI 多 worker 不会复制调度器。

用户已确认：在现有 PostgreSQL 实例中使用 MarketMind 独立数据库和专用账号，不选择与其他业务共用数据库下的 schema。具体库名、账号名和连接配置在实施时确定；本计划不授权现在创建数据库或账号，也不默认申请实例超级用户权限。

- 本地开发使用 `http://IP:端口`，Vite 将 `/api` 代理到 FastAPI；跨设备开发仅在可信局域网内开放所需端口，不使用生产凭证做公网 HTTP 调试。
- 生产服务器有公网 IP，通过域名解析到服务器，由反向代理提供 HTTPS；前端与 `/api` 同源。仅公开必要的 Web 入口，FastAPI 内部端口、Redis、浏览器控制端和数据库不直接暴露公网；证书续期由现有反向代理机制处理。
- Alembic 迁移作为独立部署步骤，不让每个 API worker 同时迁移；上线前核对生产库现有对象、授权范围及迁移可逆性，取得具体迁移操作确认后再执行。使用限定权限的应用账号，不自动覆盖现有表或重置数据库。
- 配置与秘密分离并限制访问；密钥丢失后既有加密凭证可能无法解密，需要重新登录或配置。
- 用户明确取消备份策略与备份还原验收，不配置备份周期、存储位置或 RPO/RTO，也不将其作为上线前置条件。数据库损坏、误删或不可逆迁移可能造成永久数据丢失；源站历史不保证可重新采集。任务中断续作、租约接管与受控重启继续保留。
- 任务进程崩溃的恢复依赖任务账本，不等于数据库灾难无数据损失；两类故障分开说明。
- “直接接生产数据库”指正式采集落库目标，不授权在生产环境做故障注入、清库、清 Redis、模拟断连或覆盖恢复；这些验收全部在独立实例执行，生产仅做经授权的真实采集及非破坏性检查。
- 来源依赖异常只停止受影响来源的新调度；共享 PostgreSQL/Redis 整体中断才暂停依赖它们的任务。恢复后先核对任务账本再继续，不清空队列或去重表“治好”问题。

### 10.4 GitHub Actions、日期版本与源码交付

**当前交付契约**：GitHub Actions 校验日期版本并创建 GitHub 源码 Release；不构建、不推送、不附带 Docker 镜像或容器部署清单。

- 版本 tag 使用 `vYYYY.MM.DD.N`，例如 `v2026.09.19.1`。发布者按 Asia/Shanghai 选择日期及从 1 开始的当日序号；旧版本不得覆盖或改写。
- Pull Request 与默认分支提交执行 Python、ESLint、TypeScript、行为测试和构建检查。日期 tag 只有在检查通过且提交属于远端默认分支历史时才创建 Release。
- Release 使用 GitHub 自动生成的变更说明，只交付 GitHub 自动提供的源码归档；不上传凭证、环境文件、数据库内容、登录会话或本地运行产物。
- 已存在的 Release 必须拒绝覆盖；发布响应不确定时先核对远端状态，不删除或重建同名版本。
- 生产服务器从指定 tag 检出源码，使用锁文件安装依赖，单独执行经确认的 Alembic 迁移，构建前端静态文件，并由受控的进程管理器运行 API、调度器和各 worker。
- `.env.production.example` 仅提供无凭证的源码部署配置字段。填好的 `.env.production` 必须置于 Git 之外并限制为服务账号可读。
- 生产入口仍由反向代理提供同源 HTTPS；FastAPI、Redis、PostgreSQL、浏览器控制端和 worker 不直接暴露公网。

**生产更新顺序**：选择源码 tag → 核对变更与迁移 → 暂停调度并完成在途事务 → 执行已确认的迁移 → 安装锁定依赖并构建前端 → 重启受影响进程 → 检查域名访问、版本、API 就绪和来源状态 → 恢复采集。

**回退边界**：保留上一个源码 tag 与运行配置。数据库结构兼容时可切回旧源码；破坏性迁移不能靠切换 tag 恢复数据。在未配置备份的前提下，不承诺恢复被破坏的数据；不可逆变更必须单独说明风险并取得授权。

**实施验收**：确认 tag、GitHub Release 和提交 SHA 一致；在隔离环境从该 tag 安装并运行，验证迁移、API、前端及各 worker。源码发布成功不等于生产部署完成。

## 11. 实施顺序与交付门槛

```text
P0 六入口访问与金十登录验证
        |
P1 基础工程 + 数据/任务/API 契约
```

### P0：可行性与授权边界

- 逐入口确认有效列表、分页、详情、源 ID 和时间字段。
- 实测金十真实二维码登录、两个域名的登录验证与会话失效路径。
- 记录许可、限速与内容边界；确认历史回补实际能力。
- 交付六入口采集协议说明和脱敏样本。任何入口无法完成时明确阻塞原因，不以其他来源代替验收。

### P1：基础工程与持久化契约

- 建立 FastAPI、Scrapy、前端、PostgreSQL、Redis 和迁移工程；区分隔离验证配置与生产连接配置，不在工程初始化时连接或改动生产库。
- 前端按参考项目模式使用 Element Plus、UnoCSS、`@antfu/eslint-config`。
- 完成统一新闻/修订模型、任务账本、管理鉴权和 OpenAPI 基线。
- 锁定模块接口后才能并行适配，避免三个来源形成三套字段或错误模型。
- 准备容器构建与 GitHub Actions 检查/发布方案，构建入口与三个来源进程隔离保持一致；实际仓库权限和服务器架构在实施时核实。

### P2：来源适配器

- 华尔街见闻：新闻与快讯；财联社：深度与电报；金十：快讯与文章。
- 各来源实现增量、有限回补、正文状态、去重、修订、解析异常检测。
- 三个来源可以独立开发；共享模型和公共中间件由单一负责人维护。
- 三个来源上线运行相互独立；一个来源适配未通过不能伪报整体验收成功，但不阻止已通过来源在确认后运行。

### P3：调度、代理与恢复

- 完成定时 run、控制指令、租约恢复、Redis 重建、失败任务查询和重试。
- 完成代理增删改查/导入、来源有序代理绑定、故障切换开关、耗尽直连/暂停选择、共享限速、健康隔离和登录粘性出口。
- 验证停止、恢复和重启不会产生并发旧实例写入。
- 验证三个来源执行器、队列、数据库预算和来源内变更序号隔离；任何一路失败时其余两路持续入库。

### P4：最小操作页与登录

- 完成单管理员、运行监控、固定控制动作、代理管理、自定义范围回补、只读采集数据页面及后台/Telegram 告警配置。
- 代理设置页支持按来源排序代理、开关故障切换、选择耗尽后直连或暂停，并显示实际出口；后台显示发布日期版本和提交 SHA。
- 展示真实登录二维码、到期刷新和分域会话状态。
- 页面使用第一阶段正式接口，第三阶段不重新设计同一控制面。

### P5：统一验收

- 完成下节故障演练及六入口实际抽样。
- 验证 GitHub Actions 日期版本源码 Release、本地 IP+端口访问及生产域名 HTTPS 配置；流水线不直接部署生产。
- 连续运行至少 24 小时，报告请求量、成功率、数据量、延迟、正文状态、异常和实际覆盖范围。
- 使用 OpenAPI 和必要的简短部署、任务运行恢复及操作说明完成交付，不重复编写企业级流程文档；备份策略和备份还原已按用户决定排除，记录真实外部访问或登录限制。

## 12. 验收清单

以下均为未来实施的验收要求，本次没有执行这些测试。

| 场景 | 通过标准 |
| --- | --- |
| 六入口采集 | 每个入口独立取得真实新闻并落库；与同一时点可见列表抽样核对，目标每入口 20 条，不足则全检并记录实际数量 |
| 来源故障隔离 | 在隔离环境分别令任一路解析失败、等待登录、超时或终止执行器，其余两路仍按计划获取并入库；单路重启和回补积压不停止其他来源 |
| 回补交互 | 默认优先回补最近 48 小时；模拟停机超过 48 小时，只自动补最近窗口并提示更早缺口；网页可指定更早范围续作、暂停/恢复，实时任务不被阻塞 |
| 内容边界 | 普通正文、会员限制、外站链接、缺时间字段均有真实样本和正确状态，不用摘要冒充全文 |
| 重复采集 | 同批数据重复执行不增加新闻身份数量；修订和入口出现关系符合实际变化 |
| 内容更新 | 同一新闻修改生成新 revision；旧版本可查询，第二阶段变更流能读到新版本 |
| 故障恢复 | 请求出队后、解析后、事务提交前后分别终止 worker；恢复后未完成任务可再执行，已提交新闻不重复 |
| 有限自动重启 | 隔离环境中同来源滚动 30 分钟最多自动拉起 3 次，耗尽后暂停且通知；时间窗口过去或执行器重启不能绕过暂停，管理员恢复后可继续，其他来源不受影响 |
| Redis 丢失 | 测试环境清空任务 Redis 后从账本恢复未完成工作，不丢检查点；仅在隔离环境执行破坏性演练 |
| PostgreSQL 中断 | 不把未提交任务标成功，不无限占内存；数据库恢复后可继续 |
| 增量游标 | 来源内并发事务逆序提交、同发布时间、迟到新闻和修订不会漏读；跨来源公平分页，一来源事务卡住不阻止另两路提交和消费 |
| 代理与限速 | 默认无代理直连；指定代理按顺序使用；开关关闭不尝试下一代理，开启可切换；全部不可用分别验证用户选择的直连和暂停，不能使用未指定代理；429 后保持来源退避 |
| 登录闭环 | 真二维码可由用户扫码，受保护请求验证成功再恢复采集；二维码过期、会话过期、双域名不同状态均可正确呈现 |
| 出口切换与会话 | 备用代理及回退直连后先验证金十会话，失效进入扫码等待；其他来源继续，切换与直连回退在后台可见且有告警 |
| 人工干预 | 页面可暂停、恢复、取消、重启、重试失败任务；返回可追踪命令，旧实例不能迟到提交 |
| 只读采集数据页 | 可按来源、发布时间和正文状态筛选，分页查看正文、原链接和修订；无编辑/删除/发布操作，原始 HTML 不作为可信脚本执行 |
| 安全边界 | 未认证无法控制采集/读取二维码；凭证不出现在 API、日志和队列；恶意 URL/HTML 不触发内网访问或脚本执行 |

### 16.3 页面操作与异步结果

- **来源/采集器**：配置来源共享请求间隔、出口策略及入口计划；提交使用当前 `config_version`，冲突后刷新重试。空代理列表直连；先在代理页建库存，再在来源页排列 `proxy_ids`，明确故障切换开关与 `direct/pause` 耗尽策略，不会随机使用库存里的其他代理。
- **运行**：选择入口立即采集或范围回补；页面输入北京时间（UTC+8），结束时间不包含在范围内。详情查看统计、检查点、覆盖缺口、任务及日志；暂停/恢复/取消、采集器重启、失败任务重试都有持久化异步命令。先看 `command_id` 对应结果，再看 run 与实际进度，HTTP 202 不是完成证明。自动恢复预算耗尽或来源被暂停时，修复原因后显式恢复/重启，不靠重启容器或等待时间过去解锁。
- **代理健康检查**：启动 `marketmind.proxy_runtime` 后，在代理页点击健康检查。结果按来源区分，检查完成不等于每个来源均健康；查看 `result.items`。添加库存不改变来源出口，健康恢复也不自动解除已暂停来源。
- **金十登录**：启动 `marketmind.session_worker`，在扫码页创建官方登录尝试，由用户手机扫码确认；查看两个域名的实际认证状态。二维码过期后刷新，取消或撤销会话会停止使用旧版本。worker 重启后复验保存的会话，不直接信任此前 `authenticated`。不得把 CLI 导入、二维码展示或未完成扫码算作登录恢复验收。
- **后台告警/Telegram**：配置并保存目标与 Token；保存本身不发送测试通知。启动 `marketmind.notification_worker` 后，由管理员显式点击测试并跟踪投递结果；即使常规通知关闭，显式测试仍可能发送。通知进程与采集解耦，失败不回滚新闻事务。`--health-only` 仍会探测依赖、补记故障，并可能发送依赖故障通知，不是无副作用演练模式；`--once` 只执行一个周期，不保证排空 outbox。

手动调用 API 时统一加 `/api/v1`，使用管理员会话及写操作的 Origin/CSRF，异步创建还需 `Idempotency-Key`；优先使用管理页避免把认证秘密写进命令行。异步结果必须按类型查询：运行控制用 `GET /commands/{command_id}`，代理检查用 `GET /proxy-checks/{command_id}`，通知测试用 `GET /notification-deliveries/{command_id}`；不能把所有 ID 都送往 `/commands`。
